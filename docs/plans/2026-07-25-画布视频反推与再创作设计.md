# Infinite Canvas 视频反推与再创作设计

> 本文档是项目后续视频反推、分镜生成、逐镜头生成、旁白时间轴和成片合成工作的设计基准。设计思路变化时，应直接审查并修订相关章节，删除、合并或改写过时内容，确保全文始终一致，不并列保留互相冲突的新旧方案。

## 1. 核心决策

Infinite Canvas 保持独立演进，不与 OpenMontage 合并，不引入 OpenMontage 源码、Pipeline、Skills、Checkpoint、Backlot 或 Agent Runtime 作为项目依赖。

项目继续沿用现有轻量架构：

```text
浏览器 Infinite Canvas
  ├─ 读取和保存本地画布项目
  ├─ 浏览器直连用户配置的模型接口
  ├─ 将反推结果转换为可编辑节点和连线
  └─ 管理图片、视频、音频生成任务
          ↕ HTTP
Windows 本地媒体服务
  ├─ Deepgram 原片语音识别与字词时间戳标准化
  ├─ 音频分析
  ├─ 视频标准化
  ├─ 旁白时间轴对齐
  └─ FFmpeg 合成完整视频

可选 Canvas Agent / Codex
  └─ 通过现有画布工具辅助用户操作，不参与核心流程运行
```

画布既是用户的编辑界面，也是视频生产流程的可视化状态。项目不再建设独立的服务器生产状态机、OpenMontage Orchestrator 或多租户 Agent 平台。

## 2. 目标

用户上传或选择一条原始视频后，可以在画布中完成：

- 反推视频概要、视觉风格、原始文案、台词、旁白和镜头结构。
- 根据用户要求改写文案并生成新的逐镜头提示词。
- 将结果创建为可编辑的文本、音频配置和视频配置节点。
- 独立修改并重新生成任意镜头。
- 使用统一旁白作为成片主时间轴。
- 将多个生成视频、旁白和字幕时间信息合成为完整视频。
- 保留每个镜头的提示词、参数、生成结果和连接关系，方便人工检查和调整。

核心体验不是完全隐藏过程的一键黑盒，而是让用户在画布上看见并控制每一步，同时减少重复操作。

## 3. 非目标

当前设计不包含：

- 引入或改造 OpenMontage。
- 建设服务器内置 Agent Runtime。
- 使用 OpenMontage Pipeline、Skills、Artifact 或 Checkpoint 模型。
- PostgreSQL、Redis、S3 / MinIO 和多 Worker 服务架构。
- 云端多用户项目同步、多人协作或服务器任务恢复。
- 多 Agent 角色协作。
- 让 Agent 获得任意 Shell、文件或数据库权限。
- 一次性发布到第三方内容平台。

如果未来需要云同步或多人协作，应单独设计 New Canvas 自身的服务端能力，不以接入 OpenMontage 为前提。

## 4. 视频反推流程

```text
原始视频节点
  ↓
视频理解模型脚本
  ↓
结构化反推结果
  ├─ 视频概要与原文案
  ├─ 改写文案
  ├─ 标题与话题
  ├─ 台词与旁白
  └─ 逐镜头描述和生成提示词
          ↓
分镜文本节点 01 → 视频配置节点 01
分镜文本节点 02 → 视频配置节点 02
分镜文本节点 N  → 视频配置节点 N
台词与旁白节点 → 音频配置节点
```

前端读取视频节点的 Blob/File，并通过用户配置的视频理解模型脚本发送完整视频。模型脚本负责具体接口调用、流式读取或任务轮询，前端负责：

- 校验和解析模型返回的 JSON。
- 规范化镜头时间、时长和缺失字段。
- 创建画布节点和连线。
- 填入当前视频、音频模型的默认参数。
- 保留原始响应和可操作的错误信息。

视频反推必须同时分析画面和原始音轨。镜头内存在可辨识的人声口播时，模型不得仅因为画面是封面、字幕页或静态展示而将 `dialogue` 和 `narration` 都返回为空；应填写对应口播文本。视频理解模型返回的原片口播边界只作为估算值；用户启用本地 Deepgram 校准时，浏览器将原视频 Blob 上传到 Windows 本地媒体服务，由本地服务调用 Deepgram 原生 `/v1/listen` 接口获取字词时间戳，并按镜头画面区间回写真实口播开始和结束时间。原片口播时间用于还原原视频节奏和检查反推质量，不直接作为新成片的最终时间轴；新成片仍以重新生成的 TTS 原生时间戳为准。

Deepgram API Key 保存在 Windows 本地媒体服务配置中，不写入画布节点、项目数据或浏览器业务存储。本地服务通过受 Token 和 Origin 保护的 multipart 接口接收原视频，使用 FFmpeg 提取适合识别的单声道音轨，再向 Deepgram 上传音频二进制，因此不要求原视频具有公网 URL。Deepgram 调用失败不得阻止视频理解结果创建分镜；界面应明确提示校准失败，并继续保留标记为模型估算的原片口播时间。

原始长视频默认不作为后续每个镜头的视频参考，避免超过视频模型的参考时长限制。后续参考图或参考视频由用户在画布中单独连接。

## 5. 反推结果结构

```ts
type VideoStoryboard = {
  summary: string;
  style: string;
  originalCopy: string;
  rewrittenCopy: string;
  titles: string[];
  hashtags: string[];
  shots: Array<{
    startMs: number;
    endMs: number;
    visual: string;
    camera: string;
    action: string;
    dialogue: string;
    narration: string;
    sourceNarrationStartMs?: number;
    sourceNarrationEndMs?: number;
    sourceNarrationTimingSource?: "model" | "deepgram";
    subtitle: string;
    soundEffect: string;
    transition: string;
    generationPrompt: string;
    videoParams: Record<string, unknown>;
  }>;
};
```

当前视频生成链路的镜头时长统一规范为 4-15 秒。反推结果中不足 4 秒的镜头优先与相邻镜头合并，超过 15 秒的镜头拆分；无法继续合并的短镜头仍保留独立分镜，但视频配置的生成时长不得低于 4 秒。时间码倒序、重叠或超出视频时长时由前端规范化并给出明确提示。

`sourceNarrationStartMs` / `sourceNarrationEndMs` 使用相对原视频起点的毫秒值，必须落在对应镜头的 `startMs` / `endMs` 范围内。镜头没有人声口播时两个字段均为空；只要任一字段有效，就必须同时存在另一字段和非空的 `dialogue` 或 `narration`。`sourceNarrationTimingSource` 标记时间来源：`model` 表示视频理解模型估算，`deepgram` 表示 Deepgram 字词时间戳校准。Deepgram 返回的字词按与镜头区间重叠关系分配，镜头口播边界取该镜头首个和末个字词的时间；无重叠字词时保留模型估算结果，不猜测精确位置。

## 6. 画布节点职责

项目继续复用现有节点类型，不新增 OpenMontage 专属节点或元数据模型。

- 视频节点：原始视频、逐镜头生成结果和最终成片。
- 文本节点：概要、原始文案、改写文案、标题、分镜、旁白和成片时间轴。
- 配置节点：图片、视频和音频生成参数。
- 图片节点：参考图片和生成图片。
- 音频节点：统一旁白、音乐和其他音频素材。
- 连线：表示提示词、参考素材和生成配置之间的输入依赖。

逐镜头配置可保存：

- `storyboardId`，标识同一次反推生成的音频配置和全部视频配置，时间轴回写不得影响其他反推任务
- `storyboardShotIndex`
- `prompt`
- `narrationText`
- `sourceStartMs` / `sourceEndMs`，表示该镜头在原视频中的画面区间
- `sourceNarrationStartMs` / `sourceNarrationEndMs`，表示视频反推得到的原片人声口播区间
- `sourceNarrationTimingSource`，表示原片口播区间来自视频理解模型估算或 Deepgram 字词时间戳
- `narrationStartMs` / `narrationEndMs`，表示新 TTS 统一旁白中分配给该镜头的完整区间
- `narrationAlignmentStatus`，表示新旁白尚未匹配、已匹配或匹配失败
- `subtitleText`
- `transitionText`
- 视频时长、画幅、分辨率、声音和水印参数
- 当前生成状态和错误信息

画布节点 ID 和连接关系就是当前工作流的编辑依据，不再增加另一套 Run、Stage、Artifact 和节点映射状态。

## 7. 逐镜头生成

每个分镜使用独立的视频配置节点。用户可以：

- 修改分镜描述和生成提示词。
- 连接参考图片、参考视频或参考音频。
- 调整模型、时长、比例、分辨率、声音和水印。
- 单独生成或重新生成某个镜头。
- 批量选择配置节点触发生成。
- 查看任务状态、失败原因并重试。

生成任务继续使用项目现有模型接口和任务状态机制。固定步骤由前端和配置节点执行，不通过 Agent 自主选择供应商或改写任务。

所有异步视频生成任务提交成功后统一每 30 秒查询一次状态，避免 Seedance 原生、OpenAI 兼容和中转渠道高频轮询。首次任务提交仍立即执行，只有后续状态查询等待该间隔；用户取消任务时应立即终止等待和后续请求。

视频渠道支持 `OpenAI`、`Gemini` 和 `Seedance` 三种渠道协议。请求地址按渠道协议规范版本路径：OpenAI 使用 `/v1`，Gemini 使用 `/v1beta`，Seedance 使用 `/api/v3`；裸 Base URL 自动补齐版本路径，填写了其他渠道版本路径的地址则替换为当前渠道版本。`Seedance` 是渠道级协议，适合建立只包含 Seedance 视频模型的独立渠道；该渠道中的视频生成最终固定调用 `/api/v3/contents/generations/tasks` 创建和查询任务，不再根据模型名称或 Base URL 猜测协议。请求使用 Seedance 原生 `content`、`ratio`、`resolution`、`duration`、`generate_audio` 和 `watermark` 字段，并支持现有参考图片、参考视频和参考音频结构。反推分镜创建的视频配置固定关闭生成声音，因此 Seedance 请求必须发送 `generate_audio: false`；普通视频配置继续由画布中的“生成声音”开关决定该字段。

`OpenAI` 渠道继续调用 `/v1/videos` 兼容协议。OpenAI 视频协议没有统一的原生声音控制字段，程序不得假设该协议支持 `generate_audio`；需要可靠控制 Seedance 声音、参考媒体或原生任务参数时，应使用独立的 `Seedance` 渠道。`Gemini` 渠道当前仍不用于视频生成。

## 8. 统一旁白与成片合成

统一旁白作为最终视频的主时间轴：

```text
台词与旁白文本
  ↓
统一 TTS 音频
  ↓
读取 TTS 字词时间戳 / 回退分析停顿和语句边界
  ↓
将每个视频镜头对齐到旁白语句
  ↓
裁剪过长视频 / 补齐过短视频
  ↓
合并画面并替换为统一旁白音轨
  ↓
完整成片 + 成片时间轴
```

生成旁白时，支持字幕对齐的 TTS 接口应同时请求字词时间戳，并将标准化后的时间轴保存在对应音频节点 metadata 中。时间戳统一使用相对音频起点的毫秒值，至少包含文本、开始时间和结束时间；供应商返回置信度时一并保留。重新生成音频时必须同步覆盖旧时间轴，避免音频与字幕数据错配。

存在字词时间轴的音频节点应提供“字词时间轴”查看入口。入口保持音频节点本身简洁，点击后通过弹窗展示完整旁白以及每个字词的文本、开始时间、结束时间和可选置信度；没有有效时间戳时不显示入口。该界面只用于检查已有数据，不在展示时重新请求接口或重新分析音频。

音频接口协议由渠道中的音频模型固定配置，不放到每个画布节点重复选择。Seed TTS 支持两种调用模式：

- OpenAI 兼容模式：继续请求渠道的 `/v1/audio/speech`，用于只需要音频或中转服务未开放原生接口的场景。
- V3 时间戳模式：请求渠道的 `/api/v3/tts/unidirectional`，使用 New API Token 作为 `X-Api-Key`、模型名作为 `X-Api-Resource-Id`，并固定发送 `enable_subtitle: true`。前端逐行解析 NDJSON 响应，合并 Base64 音频分片并保存 `sentence.words` 时间戳。

模式切换只改变对应模型的请求协议，不改变音频节点的数据结构。已有模型默认保持 OpenAI 兼容模式；只有用户明确为模型选择 V3 时间戳模式时才使用原生接口。V3 响应必须收到完成标记后才视为成功，避免上游中断时保存不完整音频或时间轴。

成片对齐优先使用音频节点已有的 TTS 原生字词时间戳。程序按分镜顺序规范化 `narrationText` 和字词文本，忽略空白及不影响语义匹配的标点，在完整字词序列中执行连续、单向匹配；每个分镜使用首个匹配字词的 `startMs` 和末个匹配字词的 `endMs` 形成旁白区间。匹配必须保持分镜顺序，后一个分镜不能复用前一个分镜已经消费的字词。

原片口播区间与新 TTS 口播区间是两套独立数据。`sourceNarrationStartMs` / `sourceNarrationEndMs` 只描述原视频中实际听到人声的位置，用于检查视频反推是否漏掉或错分口播；`narrationStartMs` / `narrationEndMs` 来自重新生成的 TTS 字词时间戳，用于控制新视频的镜头时长和最终合成。新 TTS 对齐不得覆盖原片口播区间，也不得直接复用原片毫秒值。

原生时间轴存在但个别分镜无法可靠匹配时，不猜测字级位置，也不调用大模型进行语义时间对齐；整次成片任务回退到现有本地媒体服务的停顿分析和语句边界推导，避免同一成片混用两套时间基准。时间戳缺失或无效不应阻止音频生成成功。

字级时间戳不直接拼接到视频生成提示词。视频提示词继续描述画面、人物动作和运镜；程序将匹配得到的镜头时长转换为 4-15 秒的生成参数。旁白区间不足 4 秒时仍生成 4 秒视频，再由成片阶段裁剪到实际旁白区间；超过 15 秒时生成 15 秒视频，并由成片阶段按现有补齐策略覆盖剩余时长。模型支持分阶段动作描述时，只允许生成秒级的相对动作节拍，例如“0-2 秒人物进入画面，2-5 秒镜头推进”，不发送逐字毫秒时间码。

视频反推创建节点时，应为音频配置和全部视频配置写入同一个 `storyboardId`，并将镜头原始区间、原片口播区间和旁白文本写入视频配置。统一旁白生成成功后，程序只匹配并更新该 `storyboardId` 下按 `storyboardShotIndex` 排序的视频配置，回写 `narrationStartMs`、`narrationEndMs`、`narrationAlignmentStatus` 和限制在 4-15 秒的生成秒数；匹配成功后明确提示已应用的分镜数量。匹配失败时不修改提示词正文，保留原片口播区间，并在对应配置中持久显示失败原因。反推结果中的镜头明明存在原片人声但 `narrationText` 为空时，应视为反推信息缺失，不得解释为静音镜头或假装已经应用 TTS 时间轴。

视频配置节点应直接显示时间轴摘要，使用户不依赖一次性的消息提示即可检查对齐状态：原片镜头区间、原片口播区间、新 TTS 旁白区间、实际剪辑时长、4-15 秒模型生成时长和匹配状态。音频节点的字词时间轴弹窗应同时显示“已应用 N/M 个分镜”；未匹配分镜应列出序号和原因。字词时间戳仍不写入生成提示词正文。

用户在画布中选择至少两个视频节点和一个旁白音频节点，通过现有本地媒体服务执行：

- 读取 TTS 原生字词时间戳，缺失时执行旁白停顿分析。
- 文本语句与有效语音区间对齐。
- 视频标准化为统一分辨率、帧率和编码。
- 根据时间轴裁剪或补齐镜头。
- 按画布选择顺序拼接视频。
- 混入统一旁白并输出 AAC 音轨。
- 创建完整成片视频节点和成片时间轴文本节点。

首版使用确定性的硬切。字幕样式、复杂转场和自动混音在基础时间轴稳定后再增加。

## 9. Agent 的定位

Canvas Agent / Codex 保持可选，不是普通用户使用视频反推和成片合成功能的前置条件。

Agent 可以通过现有结构化画布工具：

- 读取当前画布状态。
- 创建、修改和连接节点。
- 帮助整理文案和提示词。
- 触发已有图片、视频和音频生成流程。
- 查询生成任务状态。
- 按用户要求批量调整或重新生成节点。

核心业务能力必须在不连接 Agent 时仍然完整可用。项目不为视频反推单独实现自主 Agent Loop，也不将 Agent 对话状态作为生产流程的权威来源。

## 10. 状态与持久化

- 画布项目、节点、连线和业务数据继续保存在浏览器本地。
- 业务列表和较大数据使用 `localforage`，不放入 `localStorage`。
- 图片、视频和音频继续使用项目现有媒体存储方式。
- 浏览器中的生成状态和音频字词时间轴由现有 store 和节点 metadata 管理。
- 本地媒体服务只保存自身执行的临时任务和输出，不接管画布项目状态。
- 页面切换、项目切换或用户取消时，应终止相关请求并丢弃迟到结果。

当前架构不宣称支持云同步。静态网站可以被多个用户同时访问，但每个用户的数据和 API Key 分别保存在自己的浏览器中，不构成服务器多租户系统。

## 11. 错误处理与质量控制

- 视频无法读取、格式不支持或模型拒绝时显示明确错误。
- 视频理解返回非 JSON 时尝试提取 JSON，仍失败则保留响应摘要并提示修正模型脚本。
- 单个镜头字段缺失时使用空值和默认参数，不阻塞其他有效镜头。
- 生成失败只影响对应配置节点，允许单独重试。
- 合成前严格校验视频数量、旁白数量、时间轴条目和素材可读性。
- 本地媒体服务返回的任务结果必须与当前项目和请求匹配，避免迟到结果写入错误画布。
- 自动检查优先采用确定性规则；需要额外模型判断的视觉质量检查后续按实际需求增加。

## 12. 后续实施顺序

### 阶段一：完善反推结果和节点流程

- 按真实使用需求增加可选质量检查。

## 13. 最终结论

项目回到 Infinite Canvas 原生的视频生产思路：

```text
浏览器负责视频理解、节点工作流和模型生成
画布负责看见、编辑和组织整个生产过程
本地媒体服务负责 Deepgram 原片转写、音频分析和最终合成
Canvas Agent 只提供可选的高级操作入口
```

OpenMontage 不进入 New Canvas 的产品架构、运行链路、源码目录或部署依赖。后续实现优先复用当前画布、模型脚本、任务状态和本地媒体服务能力，避免为了完整视频生产引入另一套状态机和服务器平台。
